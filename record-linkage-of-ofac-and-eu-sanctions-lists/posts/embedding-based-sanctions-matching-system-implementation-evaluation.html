Introduction

In Part 1 of this series, we defined the experimental framework for comparing entity matching systems in the context of sanctions screening. In Part 2, we implemented and evaluated a classical string-similarity pipeline and showed that part of its recall loss was structural, driven by the blocking strategy rather than by similarity threshold tuning.

This post evaluates an alternative architecture based on text embeddings and vector similarity search. The objective is not merely to compare F1 scores, but to assess whether an embedding-based approach can relax some of the structural constraints identified in the classical pipeline while remaining computationally feasible.

Model Selection and Embedding Computation

The embedding model selected for this evaluation is dell-research-harvard/lt-wikidata-comp-multi, available on Hugging Face.

This model was chosen for three main reasons:

  • It is trained specifically for entity comparison tasks.
  • It is multilingual, which is essential given the presence of non-Latin and multi-language names in sanctions lists.
  • It leverages Wikidata-aligned training data, making it well suited for real-world entity representations.

As a first step, we computed embeddings for all entities in the OFAC and EU sanctions lists. This process involved encoding each entity's name into a fixed-length vector representation using the selected model. Implementation details are available in the script text_embeddings_computation.py.

Vector Similarity Search

To generate candidate pairs, a FAISS index was built using the embedding vectors of one dataset (e.g., OFAC). The embeddings of the other dataset (e.g., EU) were then queried against this index using a range search strategy. Pairs were retrieved when their cosine similarity exceeded a minimum threshold of 0.7. This threshold defines the minimum similarity required for a pair to be considered a candidate. The implementation deails can be found in the script text_embeddings_confusion_matrix.py.

Evaluation

We follow the same evaluation framework as in Part 2. However, in this architecture the total number of false negatives is decomposed into:

  • FN_THRESHOLD: candidate pairs retrieved from the vector index but classified as non-matches because their similarity falls below the selected operating threshold.
  • FN_IN_MINTHRESHOLD: true matches whose cosine similarity is below the minimum retrieval threshold (0.7) and are therefore never retrieved from the index.

This decomposition is conceptually analogous to the distinction introduced in the classical pipeline, but the underlying mechanisms differ.

In the classical system, FN_BLOCK originated from deterministic attribute-based filters (e.g., year of birth or normalized city) that excluded pairs before any similarity scoring took place. These exclusions were rule-driven and structurally defined.

In the embedding-based system, pairs are not excluded by predefined attributes, but by insufficient similarity under the minimum retrieval threshold. The constraint is therefore implicit and similarity-driven rather than rule-based.

The full confusion matrix is available here and the implementation code can be consulted at text_embeddings_confusion_matrix.py.

Conclusions

The embedding-based system achieves maximum F1 at a threshold of 0.95 for both individuals and organizations. The recall at this operating point is 0.82 for individuals and 0.71 for organizations. Those levels may be operationally insufficient in high-sensitivity compliance contexts. Decreasing the threshold improves the recall, but at the cost of increased false positives. For example, a threshold of 0.7 yields a recall of 0.998 for individuals and 0.967 for organizations but the number of false positives is 342,543 for individuals and 14,193 for organizations which means a great operational cost for the teams that have to deal with these false positives.

For individuals, only 4 out of 2,129 true matches fall below the minimum similarity threshold of 0.7, yielding a theoretical maximum recall of 0.998. For organizations, 30 out of 910 true matches fall below this threshold, corresponding to a maximum recall of 0.967.

Comparisons below the 0.7 threshold indicate major differences between EU and OFAC names. For example, OpenSanctions lists EU.9725.71 (EU) and 43316 (OFAC) as the same person, but the EU name is VJATJESLAV VJATJESLAVOVITJ DUCHIN, while OFAC lists PAVEL VIKTOROVICH AKIFEV, with a similarity score of just 0.38. If this is not an OpenSanctions error, detecting the match based solely on name similarity would be very difficult.
